# Repository Quality Standard

## Purpose

This repository is maintained as an operational knowledge base rather than a link dump. Every item must help a participant, organizer, mentor, judge, or educator complete a concrete hackathon task.

## Resource acceptance gates

A resource is eligible only when it has a stable canonical URL, a clear owner or maintainer, a specific hackathon use case, enough documentation to evaluate it, and no unresolved integrity or safety concern. Official documentation is preferred. Primary project sources are accepted when they are more useful than marketing pages. Community resources require stronger editorial justification.

## Editorial requirements

Descriptions must be factual and neutral. Pricing summaries are approximate and must not be presented as guarantees. Entries must disclose whether they are official, primary, or community maintained. Affiliate links, tracking parameters, copied marketing copy, SEO filler, and paid placement are prohibited.

## Engineering requirements

All generated catalog views must match the canonical JSON data. Internal links must resolve. JSON and workflow files must parse. Repository automation must use least-privilege permissions, reject unsafe pull-request execution patterns, and produce checksum-protected release archives.

## Maintenance requirements

Active entries receive editorial review at least every 180 days. Automated link checks run weekly. A working URL does not by itself prove that a resource is still useful, safe, affordable, available in every region, or eligible for a specific event.

## Removal criteria

Remove or archive entries that are abandoned, misleading, malicious, permanently unavailable, duplicative without a clear advantage, or no longer relevant to hackathon delivery. Deprecation notes should point to a suitable alternative when possible.

## Evidence over volume

Resource count is not a success metric. A smaller, maintained set with clear use cases is preferable to a large collection of weak or stale links.
