# Curation Policy

## Inclusion requirements

A resource must:

- Solve a clear hackathon participant, mentor, judge, or organizer need.
- Use an official or primary project URL whenever possible.
- Have accessible documentation or onboarding.
- Be legally usable and not primarily deceptive, malicious, exploitative, or designed to bypass event rules.
- Include a factual description and a specific practical use case.
- Disclose submitter affiliation.
- Add distinct value beyond existing entries.

## Source types

- `official`: controlled by the product, project, standards body, dataset owner, or event organizer.
- `primary`: the canonical repository, publication, dataset, or project source when no separate official documentation exists.
- `community`: a maintained directory or educational collection with clear editorial value.

Community sources receive additional scrutiny and should not replace available official documentation.

## Exclusions

- Referral links, URL shorteners, copied lists, unlicensed asset collections, piracy, credential sharing, spam, or unverifiable claims.
- Tools whose primary purpose is cheating, surveillance, malware, harassment, manipulation, credential theft, or unauthorized access.
- Abandoned or unsafe projects without a stable archival reason.
- Duplicate products without a distinct use case.
- Temporary pricing claims presented as guarantees.

## Editorial review

Active entries should be reviewed at least every 180 days. Review includes URL ownership, current purpose, documentation quality, maintenance, cost summary, security or policy concerns, duplicate coverage, and relevance to time-boxed projects.

Maintainers may deprecate, archive, replace, or remove resources after material policy changes, security concerns, loss of maintenance, misleading marketing, broken primary sources, or reduced relevance. Inclusion is editorial, not permanent or an endorsement.
